# ЗАДАЧА: найти и устранить все проблемы и пробелы, которых не должно быть в нормальном лаунчере

Ты — QA-инженер + разработчик в репозитории `mc-launcher-v2` (Tauri 2 + React 19/TS + ядро Rust). Лаунчер собран и работает: запуск vanilla/Fabric/Forge/NeoForge/модпаков, каталог Modrinth, офлайн/MSA-профили, темы «Сланец», NSIS. Владелец уже поймал на живом использовании три бага (залипший статус «Запущено», отсутствие бесконечного скролла, Главная-дубликат) — они исправлены, но сам факт показателен: **автоматические приёмки не ловят проблемы реального использования**. Твоя задача — найти ВСЕ такие проблемы до того, как их найдёт владелец. В отличие от прошлых задач, **Rust-ядро трогать МОЖНО** (с тестами).

## 0. Железные правила

1. **Никакого фейка в UI** (элемент без реальных данных = провал). Пустые состояния честные.
2. **Скачивание только по хэшам** с официальных серверов; зеркала без хэшей запрещены; ноль инжекций в игру; секреты/токены не попадают в git, логи и экран.
3. **Каждый фикс = repro + корень + проверка.** Не «поправил на глаз»: сначала воспроизвести, потом чинить, потом прогнать сценарий ещё раз.
4. i18n ru+en для всех новых строк; контраст ≥4.5:1; цели ≥40px; фокус видим; `prefers-reduced-motion`.
5. Атомарные коммиты (`Fix: …` / `Audit: …`), приёмки `scripts/m4_acceptance.cjs`, `m5_acceptance.cjs`, `ui_checks.cjs`, `kill_acceptance.cjs`, `scroll_test.cjs` обязаны остаться зелёными (если ты меняешь селекторы — обновить, не ослабить).
6. CDP-порт для автотестов включать временно в `tauri.conf.json` (`additionalBrowserArgs: "--remote-debugging-port=9223"`) и **снимать перед сдачей**. Перед CDP-запуском убивать работающий экземпляр лаунчера (single-instance перехватывает второй).
7. Реестр проблем вести в `AUDIT.md` с первой находки (см. §5).

## 1. Известные зацепки (начни с них — это не весь список)

## 2. Метод: тестируй как злой пользователь, не как тест-сьют

Приёмки идут по счастливому пути. Твоя ценность — пути несчастливые. Для каждой категории ниже: составь сценарии → выполнишь руками/через CDP → зафиксируй результат в `AUDIT.md` → почини → добавь регресс-проверку (скрипт в `scripts/` или юнит-тест).

Гонки и повторные действия:
- Двойной клик по «Играть» (два запуска одного инстанса?), «Играть» на втором инстансе пока первый запущен (параллельные инстансы — спека §6.10 требует поддержку), Стоп во время «Подготовка/Загрузка», удаление во время загрузки, дублирование запущенного, перезапуск сразу после Стопа (`.lock` успевает удалиться? PID переиспользован?).
- Закрытие лаунчера при запущенной игре: игра обязана продолжить жить, а после перезапуска лаунчер обязан показать «Запущено» (восстановление по `.lock`/`process_status`) и Стоп должен работать.
- Убийство игры извне (диспетчер задач) — статус в UI должен упасть в « exited» за разумное время.
- Быстрое переключение страниц во время загрузок/установки; смена темы/профиля посреди операции.

Сеть и носители:
- Офлайн с самого старта (запуск установленного инстанса без сети обязан работать); обрыв сети в середине скачивания (продолжение/повтор, не «вечная загрузка»); таймауты Modrinth; повреждённый файл в сторе (хэш-мисматч → перекачка, не краш); диск переполнен (осмысленная ошибка).
- Прокси из настроек: реально применяется ко всем запросам ядра?

Windows-специфика:
- Каталог данных в пути с кириллицей/пробелами/длинным путём (>240 симв.), на OneDrive-синхронизированной папке; ник профиля с юникодом/эмодзи/рег._case; имя инстанса с запрещёнными символами файловой системы (`<>:"/\|?*`, точка в конце) — валидация при создании/переименовании.
- Анти-фринж: повторный запуск установщика поверх установленной версии; установка в путь с не-ASCII.

UI-пробелы против ядра: см. §1 — составь ПОЛНУЮ таблицу «команды ядра → есть ли в UI» (grep `invoke` vs `generate_handler` в lib.rs), закрой критичные.

## 4. Производительность и устойчивость UI

- Каталог модов: скролл до 200+ строк — нет ли деградации (виртуализация `@tanstack/react-virtual` уже в зависимостях — применить при необходимости); лог инстанса в 10+ МБ в UI (если покажешь — только хвост, `logsTail`).

## 5. Формат работы и реестр

`AUDIT.md` в корне репо, пополняется по ходу:

| # | Категория | Симптом (что видит юзер) | Repro | Корень | Фикс (коммит) | Проверка | Приоритет |
|---|-----------|--------------------------|-------|--------|---------------|----------|-----------|

Порядок: P0 (потеря данных/краш/навсегда залпшее состояние) → P1 (сломанная функция) → P2 (неудобство) → P3 (полировка). P0–P1 чинишь сам; P2 — чинишь если ≤ ~50 строк; P3+ — только записываешь. Каждая строка реестра должна иметь repro, иначе это не находка, а гипотеза — проверь прежде чем писать.
